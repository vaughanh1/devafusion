## Next.js & React Boundaries

- **App Router only:** Focus on the App Router ecosystem.
- **Server-First, Leaf-Isolated Client Boundaries:** The codebase is React Server Component (RSC) first by default. `'use client'` is a deliberate performance cost, not a default — never mark an entire route file or a structural layout container as a Client Component; isolate interactivity to the smallest leaf node that needs it (e.g. a single `<ThemeSelector />` button group, not the section that contains it — see `theme-selector.tsx` and the Accessibility Theme Engine section below). Do not over-nest client state. Never execute a database query, translation/parsing logic, or non-trivial array filtering inside a `'use client'` boundary — that work belongs on the server.
- **Hydration-Safe Client Reads:** A client component reading browser-only state (storage, cookies) must not introduce a visible flash or a hydration mismatch. Prefer `useSyncExternalStore` (see `cookie-banner.tsx`) or a lazy `useState` initializer that reads the same source a pre-hydration inline script already wrote to the DOM (see the Accessibility Theme Engine section). A plain mount-guard `useEffect` is a fallback only, since it re-renders after first paint and produces a visible flash.
- **Standalone Output Target:** Every modification to `next.config.ts` must preserve or enforce the `output: 'standalone'` setting. This is mandatory to ensure the application compiles to a self-contained, container-ready Node.js server.
- **No Raw Script Tags:** Never inject raw `<script>` tags for tracking into the HTML head. Frontend tracking must leverage native Next.js framework libraries (e.g., `@next/third-parties`) so client-side route transitions are captured without resetting the user session. The one sanctioned exception is the fixed, literal flash-prevention script described in the Accessibility Theme Engine section — it exists specifically because it must run before any framework script loads.
- **Explicit Server Error Handling:** All Next.js Server Components and server actions that perform data fetching or mutations must handle errors explicitly using `try/catch` blocks. Do not let unhandled promise rejections propagate; they can escape server telemetry hooks in a containerized environment.

## Database, Schema Sharing & Future Forms

- **Backend-first schema, never client-imported:** any Zod schema derived from a Drizzle table (`drizzle-zod`'s `createInsertSchema`/`createSelectSchema`, e.g. `db/schema.ts`, `features/*/schema/*.zod.ts`) must carry an `import "server-only"` guard at the top. This is deliberate (see `docs/adr/0011-drizzle-orm-and-repository-pattern.md`): the DB table stays the single source of truth for validation, but that schema module transitively pulls in `drizzle-orm`/`pg`, which must never reach a client bundle. A `server-only` import turns an accidental client-side import into a build failure, not a silent bundle-size regression.
- **When the first real form is built (registration, feedback, contact — reCAPTCHA + MFA already on the roadmap):**
  - Use a **Server Action** as the mutation path, colocated with its route, not a client-side `fetch` to a hand-rolled API route. The action file is server code by construction, so it can import the Drizzle-derived schema directly with zero bundle risk.
  - **Server-side validation via the Drizzle-derived schema is the only authoritative check** — re-validate in the Server Action even if the client also validated; never trust client input.
  - **Client-side validation is UX-only** and must not import the Drizzle-derived schema: use native HTML attributes (`required`, `type="email"`, `minLength`) for the common cases. If a rule genuinely has no DB equivalent (password-confirmation match, "reCAPTCHA token is present", a ToS-acceptance checkbox), write a small standalone Zod schema for it and compose (`.and()`/`.extend()`) with the server-side schema conceptually — do not replace the Drizzle-derived schema or duplicate its DB-derived constraints by hand.
  - Surface validation/submission errors via `useActionState`, per the existing Explicit Server Error Handling rule — no unhandled rejections.
  - Any reCAPTCHA secret key or MFA provider secret is sourced from Key Vault at runtime (root AGENTS.md, Zero Hardcoded Secrets) — only a reCAPTCHA *site key* (public by design) is ever eligible for the `NEXT_PUBLIC_` prefix below.

## Local Postgres for Migration Testing

- **Day-to-day `npm run dev` needs no manual setup** — its `predev` script (`scripts/ensure-local-postgres.mjs`) starts/reuses a persistent `devafusion-dev-local` Docker container matching `.env.example`'s `DATABASE_URL`, enables `citext`, and runs `npm run db:migrate` automatically every time. The workflow below is a separate, deliberate clean-slate check specifically for verifying a *new* migration file before pushing it — starting from a genuinely empty database, not the persistent dev one, which may already have old migrations applied from previous sessions.
- **`drizzle-kit migrate` has no local target by default** — the only real Postgres this project has is the firewalled Azure Flexible Server, and PGlite (used inside Vitest, `features/log/__tests__/`) is a WASM reimplementation, not the literal engine that will run a migration in production. Never treat a PGlite-only pass as proof a migration is safe to ship.
- **Before pushing any change under `src/web/drizzle/**`, run the migration locally against real Docker Postgres, pinned to the same major version as the live server** (`postgres_version = "16"` in `infrastructure/app/modules/postgresql/variables.tf` — check that file if it ever changes, don't assume 16):
  ```
  docker run --name devafusion-postgres-local --rm -e POSTGRES_PASSWORD=localdev -p 5432:5432 -d postgres:16
  ```
- Point `DATABASE_URL` at it for the duration of the check, then run the real script:
  ```
  # PowerShell
  $env:DATABASE_URL = "postgresql://postgres:localdev@localhost:5432/postgres"
  npm run db:migrate
  ```
  ```
  # bash
  export DATABASE_URL="postgresql://postgres:localdev@localhost:5432/postgres"
  npm run db:migrate
  ```
- Inspect the result with `docker exec -it devafusion-postgres-local psql -U postgres -c "\d log_entries"` (or any Postgres client pointed at `localhost:5432`) before trusting the migration file.
- `docker stop devafusion-postgres-local` when done — `--rm` above means it's discarded automatically, so nothing lingers between checks; each run starts from a clean, empty database, matching what a first-time `migrate` against a genuinely new table will actually see.
- This is the same "prove it against something real before it ever runs unattended in CD" posture already established for Terraform (`terraform plan`/`validate` were never trusted alone for this project's Azure-specific gaps — see the PostgreSQL zone-pinning and webhook-expiry-ceiling incidents) — a migration is Postgres's equivalent of an infrastructure change and deserves the same scepticism.

## Identity & MFA

- **Better Auth owns session/credential/OAuth core; MFA is self-built, never Better Auth's own `twoFactor` plugin.** The plugin stores its primary TOTP secret as plain text with no read-side decrypt hook (`docs/adr/0012-better-auth-identity-and-self-hosted-mfa.md`) — this project's own `features/auth/mfa/` module owns the `user_security` table (extended with `required_factors`/`mfa_frequency` for the multi-factor matrix), encrypts `two_factor_secret` transparently via the `encryptedSecretText` Drizzle `customType` (AES-256-GCM, key from `MFA_ENCRYPTION_KEY`, `features/auth/mfa/encrypted-column-cipher.ts`) before it ever reaches Postgres, and verifies codes itself via `otpauth` in `app/api/auth/two-factor/verify/route.ts`. Do not re-enable the plugin's own TOTP storage/verification path as a shortcut — it reintroduces the plaintext-secret exposure this design deliberately avoids.
- **Never call `encryptColumnValue`/`decryptColumnValue` (`features/auth/mfa/encrypted-column-cipher.ts`) outside `db/schema.ts`'s `encryptedSecretText` customType definition** — every other repository/route reads and writes plaintext through `DrizzleUserSecurityRepository`/`UserSecurityRepository`, never the cipher functions directly, keeping the encryption boundary structural rather than convention-dependent.
- **The multi-factor login flow (`login-step1` → `two-factor/verify`) withholds Better Auth's own minted session cookie in an in-memory `lru-cache` (`features/auth/mfa/mfa-session-cache.ts`, 3-minute TTL) rather than deferring session creation** — the installed `better-auth@^1.7.5` has neither a `dontCreateSession` flag on `signInEmail` nor a public `auth.api.createSession` surface, confirmed directly against its compiled source. Do not attempt to re-mint a session after MFA completes; release the cookies already captured in Step 1 instead.
- **`ACS_EMAIL_CONNECTION_STRING`/`ACS_EMAIL_MFA_SENDER_ADDRESS` are new server-side app_settings this slice introduces** (`features/auth/mfa/send-email-otp.ts`, via `@azure/communication-email`) — unlike every other secret in this project, **neither requires a manual Key Vault step**: both are Terraform-computed outputs of `infrastructure/app/modules/email/` (`azurerm_communication_service.primary_connection_string` and a verified custom domain's `donotreply@devafusion.net` sender address, with a "Devafusion" display name from `azurerm_email_communication_service_domain_sender_username`), wired straight into `web.tf`'s app_settings. Resend was evaluated and rejected first — its nearest-to-UK region is a latency-optimization choice only, storing email content in the US regardless (docs/adr/0015).
- Regenerating Better Auth's core schema (`user`/`session`/`account`/`verification`) after a config/plugin change: `npx auth@latest generate --adapter drizzle --dialect postgresql --config auth.ts --output <scratch file>`, then diff and hand-merge into `db/schema.ts` — do not let the CLI overwrite `db/schema.ts` directly, since it also contains this project's own tables (`log_entries`, `user_security`) that the generator has no knowledge of. The correct CLI package is `auth` (`npx auth@latest ...`); `@better-auth/cli` is deprecated on npm and must not be reintroduced.
- **A signed-in account with no genuinely complete MFA choice is forced to `/mfa-setup` on every route (`proxy.ts`) — the same UK GDPR Article 25 parity `requireEmailVerification` already gives email.** Better Auth's `signInEmail` always mints a real session (no `dontCreateSession` flag exists on the installed version), so this cannot be blocked pre-session the way email verification is — enforcement instead happens at the request-routing layer via `proxy.ts` (Next.js 16's current, non-deprecated file convention — `export function proxy`, not the deprecated `middleware.ts`/`export function middleware`, confirmed by actually running a build and reading its own emitted deprecation warning; `proxy.ts` defaults to the **Node.js runtime**, confirmed empirically, so a real `pg`-backed repository call works directly with no Edge-runtime workaround). The pure allowlist/completion logic lives in `features/auth/mfa/mfa-setup-required.ts` (unit-tested in isolation) — `proxy.ts` itself stays thin wiring only.
- **A `user_security` row existing is NOT the same as MFA setup being genuinely complete** — `isMfaSetupComplete` (`features/auth/mfa/mfa-setup-required.ts`) checks this correctly; do not simplify it back to a bare row-existence check. `/api/auth/two-factor/enrol` upserts a row (`twoFactorSecret` set, `requiredFactors` including `"totp"`) the moment enrolment **starts**, before any code is ever confirmed — `twoFactorEnabled` only flips to `true` once `/api/auth/two-factor/confirm` succeeds. A naive existence check would let an account through mid-enrolment, before its authenticator app has ever proven it works. Email OTP and password-only, by contrast, are only ever saved via a deliberate `/api/user/security/settings` POST that never touches `twoFactorSecret`/`twoFactorEnabled` — for those, a saved row genuinely is completion, with no separate confirmation step to wait for.
- **The TOTP QR code has no accessible fallback for a user enrolling on the only camera-equipped device they own** (their phone) — `TotpEnrolment` renders a tappable `otpauth://` deep link alongside the QR (`app/api/auth/two-factor/enrol/route.ts`'s response now includes the raw `otpauthUri`), which most authenticator apps register as their own handler. The URI scheme itself is confirmed against Google Authenticator's own published Key Uri Format spec — whether a *specific* installed app claims it as an OS-level handler was not independently verified per-app (varies by app/OS), so it is rendered as a plain `<a>`, never a script-triggered redirect, so it degrades harmlessly if nothing claims the scheme on a given device.
- **Manual local testing without real ACS credentials:** `.env.example` deliberately has no entry for `ACS_EMAIL_CONNECTION_STRING`/`ACS_EMAIL_MFA_SENDER_ADDRESS` — there is no dev-tier ACS sandbox. A plain `npm run dev` session will throw `"... is not set - cannot dispatch an email"` (caught by `runInBackgroundOrAwait`, so it logs rather than crashing the request, but no real email is ever sent) the moment sign-up, password-reset, or an MFA email-OTP challenge tries to send one. To exercise any of those flows by hand in a real browser: set `TEST_DB_ACTIONS=true` (or `TEST_MFA_FLOWS=true` for the MFA matrix specifically — `src/web/__tests__/AGENTS.md`'s documented toggles) **before** running `npm run dev`, sign up/trigger the flow as normal, then fetch the captured link/code from `http://localhost:3000/api/test-only/verification-link?email=<the email used>` instead of checking a real inbox. That route (`features/auth/test-verification-link-cache.ts`) 404s outright unless one of those flags is set — zero surface against a real deployment. This is exactly the mechanism `tests-e2e/sign-up.spec.ts`/`mfa-flow.spec.ts`/`mfa-setup-required.spec.ts` already automate; this is the same thing done manually.

## Environment Variables

- **Server-side variables** (no prefix, e.g. `DATABASE_URL`) stay in the Node.js process and are never bundled into browser JavaScript. A check for `undefined` before use is sufficient.
- **Client-side variables** (prefixed `NEXT_PUBLIC_`, e.g. `NEXT_PUBLIC_GA_ID`) are the deliberate exception: Next.js inlines their value as a literal string directly into the browser bundle at build time, making them visible to anyone who views page source. Only use this prefix for values that are safe to be fully public (e.g. a GA4 Measurement ID, which the analytics script itself exposes in a network request anyway) — never for secrets.
- Next.js does **not** fail the build if a `NEXT_PUBLIC_` variable is unset; it silently inlines `undefined`. There is no build-time safety net, so code must check for a falsy value at runtime (e.g. `if (!process.env.NEXT_PUBLIC_MY_VAR)`) and handle the missing case itself.
- If a variable is missing or empty during local development (`process.env.NODE_ENV !== 'production'`), log a descriptive `console.warn` and gracefully disable the corresponding feature. Do not crash the application.

## TypeScript & Tailwind Code Standards

- **Strict Type Safety:** The `any` type is forbidden. All props, functions, API payloads, and state objects must have explicit `interface` or `type` definitions. Leverage TypeScript utility types (`Record`, `Partial`, `Pick`) to maintain clean and reusable definitions.
- **Clean Component Structure:** Always write components as functional components. Type definitions for props and state must be declared as a separate `interface` or `type` block *above* the component function, never inline.
- **Predictable Tailwind Styling:** Apply utility classes directly in the `className` attribute. For dynamic classes, use the `clsx` or `tailwind-merge` libraries to prevent style collisions and ensure predictability. Raw string concatenation for dynamic classes is forbidden. All styling must adhere to the existing design tokens in the Tailwind theme (see `src/web/app/globals.css`).
- **File Naming:** Component and feature filenames use `kebab-case` (e.g. `site-header.tsx`), matching this project's existing files and the `eslint-config-next` default; the exported symbol itself uses `PascalCase` (e.g. `export function SiteHeader()`). This is enforced by `check-file/filename-naming-convention` in `eslint.config.mjs` — see the App Router & File Layout Enforcement section below.

## Routing, Metadata & SEO Standards

- **Strict Metadata Compilation Guard:** Every page component (`page.tsx`) must strictly implement the typed `Metadata` interface from `next`. A missing `title` or `description` in the metadata configuration is treated as a critical code violation.
- **Static Link Verification:** All internal links must use the framework-native `<Link>` component. Never use raw `<a>` tags for internal paths. Before generating a `<Link href="...">` or `router.push()` call, verify the target route actually exists in the app's file-system route tree.
- **Framework-Level Route Verification:** Use Next.js **Typed Routes** (`typedRoutes: true` — this is a stable, top-level `next.config.ts` key as of Next.js 15+; it is not nested under `experimental`). This forces TypeScript to throw an explicit compilation error during `npm run build` if an invalid or dead path string is passed to any `<Link href="...">` or `router.push()` call.
- **Automated SEO Integration Audits:** Every time a route layout is modified, verify that its viewport and OpenGraph (OG) configuration matches the unified global metadata theme, so social preview cards do not silently break.

## Accessibility Theme Engine

- **Three fixed profiles, zero new tokens:** "Obsidian" (dark), "Editorial" (light, high-readability), and "Tactical" (WCAG AAA monochrome) are three value sets for the *existing* semantic tokens (`--background`, `--foreground`, `--surface`, `--surface-border`, `--accent`, `--accent-secondary`, `--accent-foreground`, `--muted`) — never introduce parallel token names for the same concept.
- **Selector, not server read:** Profiles are switched via a `data-a11y-theme` attribute on `<html>`, declared in `globals.css` *after* the existing `@media (prefers-color-scheme: dark)` block so an explicit choice always wins over the OS default (equal-specificity selectors resolve by source order). Never read the theme cookie with `next/headers` `cookies()` in a Server Component — reading a Dynamic API in the root layout opts the entire route tree out of static generation, which regresses every statically-generated page (`log/[slug]`, `projects/[slug]`, etc.) for no benefit the client-side approach doesn't already provide. Read the cookie client-side via an inline `<script dangerouslySetInnerHTML>` in `<head>`, following the framework's own documented flash-prevention pattern (`node_modules/next/dist/docs/01-app/02-guides/preventing-flash-before-hydration.md`). This is the one sanctioned use of `dangerouslySetInnerHTML` in this codebase, and only for this fixed, literal script body — it must never be built from interpolated or user-controlled input.
- **OS default first:** With no cookie set, `prefers-color-scheme` continues to govern light/dark exactly as it does today. The theme engine is an explicit opt-in override, not a replacement for honoring browser/OS signals.
- **WCAG AAA is a verified property, not an aspiration:** every canvas/text and canvas/accent pair shipped in a profile must be checked against the real WCAG relative-luminance formula (7:1 body text, 4.5:1 headers, 3:1 UI borders/focus states) before merging — do not ship a color pair on the strength of it "looking" high-contrast. `--muted` (used for regular readable body copy across this site, e.g. descriptions, log entries) is held to the 7:1 body-text bar, not the lighter 4.5:1 bar reserved for large headers.
- **Cookie contract:** `devafusion-a11y-theme` (`obsidian` | `editorial` | `tactical`) and `devafusion-a11y-scale` (`normal` | `large` | `accessible-xl`), named consistently with the existing `devafusion-cookie-consent` cookie. Classified "Strictly Necessary" (a functional preference, not tracking or profiling) and documented on `/legal` in the same style as the existing Google Analytics cookie section. A database-backed preference store (keyed to a user account) is a legitimate future upgrade once this project has an identity/auth system — until then, an anonymous cookie is the only mechanism that makes sense, since there is no account to key a database row on.
- **Font/contrast scaling defers to the browser first:** do not build an app-level font-zoom control duplicating native browser zoom and the `prefers-contrast`/`prefers-reduced-motion` media queries the browser already exposes for free. `accessible-xl` exists as a documented, narrow override for cases native browser zoom doesn't cover (e.g. fixed-size UI chrome that ignores text-only zoom) — it is not a general-purpose replacement for OS/browser scaling.
- **Leaf-isolated control, not a layout-tree client boundary:** `<ThemeSelector />` is a `'use client'` leaf under `components/`. It sets the `data-a11y-theme` attribute on `document.documentElement` and writes `document.cookie` directly in its click handler — no `router.refresh()`, no server round-trip, since the value is never read server-side. Any local "which option is active" highlight state uses a lazy `useState` initializer reading the same cookie the inline script reads, mirroring the `useSyncExternalStore` pattern already used in `cookie-banner.tsx` — never a mount-guard `useEffect` that would flash the wrong state on first paint.
- **Color is never the sole signal:** semantic alerts (success/warning/error) pair color with iconography or a typographic change (weight, underline) — never color alone, across every theme profile including Tactical.
- **Locale routing (`[lang]` segments) and any audio/TTS feature are explicitly out of scope for this theme engine.** They are a separate, larger routing decision and must not be assumed or partially implemented as a side effect of accessibility-theme work.
- **Every UI change is checked against WCAG before merging, not just theme-profile work:** any change touching interactive elements (buttons, links, disclosures, forms, nav) or new/changed color usage must verify, and be able to show:
  - **Keyboard focus (SC 2.4.7, SC 2.4.11):** the element is reachable and operable via keyboard alone, carries the existing `focus-visible:outline-2 outline-offset-2 outline-accent` pattern (or the native equivalent, e.g. `<details>/<summary>`, a real `<button>`), and sits in a logical DOM tab order — never simulate a control with a non-interactive element (`<div onClick>`) when a native `<button>`/`<a>`/`<details>` exists.
  - **Contrast (SC 1.4.3, SC 1.4.11):** run the actual WCAG relative-luminance formula (not a visual guess) against every color pairing the change introduces or newly exposes, in the default (unset) theme *and* all three profiles - text against its background at 7:1 (this site's body-text bar) / 4.5:1 (large headers), and any non-text UI element (borders, focus rings, icons conveying state) at 3:1. If a pairing fails, that is a defect to fix or explicitly flag before merge, not something to note and move past.
  - **Screen reader / name-role-value (SC 4.1.2):** run `eslint-plugin-jsx-a11y` (already wired into the zero-warning lint gate) against the changed files, and manually confirm icon-only or decorative elements (`aria-hidden="true"` on the glyph) still expose a computed accessible name on the interactive parent (`aria-label`, visible text, or an associated `<label>`) - an icon swapped in for a text label must not silently drop the accessible name the text label provided.
  - **Form error state (SC 3.3.1, SC 4.1.2):** an invalid field must never be signalled by border/background color alone. Every `<input>` that can be in an error state carries both `aria-describedby` (pointing at the error message's own `id`, `role="alert"`) AND `aria-invalid` (a boolean, always rendered as an explicit `"true"`/`"false"` - never omitted, since `aria-invalid` has no "absent means valid" convention the way `aria-describedby`'s `undefined`-when-clean pattern does). One without the other is incomplete: `aria-describedby` alone links the field to the message but does not itself announce "invalid entry" when the field receives focus, and `aria-invalid` alone gives no way to reach the actual error text. See `components/auth/password-field.tsx`'s `isInvalid` prop and every form under `app/sign-up`, `app/log-in`, `app/forget-password`, `app/reset-password`, `app/account`, and `components/auth/mfa-challenge-form.tsx` for the established pattern - a new form with an error state follows it, not a color change alone.
  - **Touch target size (SC 2.5.8 AA by default, SC 2.5.5 AAA on opt-in, plus a per-element force override):** every interactive control (`<button>`, `<a>`, and any `<label>` wrapping a `<input type="checkbox"|"radio">`, since clicking the label activates the input) is sized via the shared `--touch-target-size` CSS custom property (`globals.css`), never a hardcoded pixel value - `min-h-[var(--touch-target-size)]`/`min-w-[var(--touch-target-size)]`. This defaults to 24×24 CSS pixels (WCAG 2.2 Level AA, SC 2.5.8) - the widely adopted legal/regulatory baseline - and `[data-a11y-target="aaa"]` on `<html>` (`ThemeSelector`'s AA/AAA toggle) opts a visitor UP to 44×44 (Level AAA, SC 2.5.5) as an explicit showcase choice, never the reverse. A short/icon-only control (a reveal toggle, a footer social icon) needs an explicit `min-w-[var(--touch-target-size)]` alongside the height one, paired with `flex items-center justify-center` so the icon/text stays centered inside the larger hit box. A checkbox/radio's own `size-4` (16px) input is not the target - the wrapping `<label>` is. **Per-element override:** an element carrying `data-touch-target-force="aaa"` is pinned to 44px regardless of the site-wide toggle - use this only for a control whose mis-tap consequence is severe/irreversible (this codebase's own example: `delete-account-form.tsx`'s permanent-delete button), never as a general substitute for respecting the visitor's own site-wide choice. Do not assume a control "looks big enough" - measure it against the active floor explicitly before merging, the same way contrast pairs above are checked against the real formula rather than eyeballed.
  - Reference: [Nielsen Norman Group's 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) for general interaction-pattern judgement calls (e.g. progressive disclosure, recognition vs. recall) that WCAG's pass/fail criteria don't cover on their own.

## App Router & File Layout Enforcement

- Directory names under `app/**` follow Next.js App Router conventions (`check-file/folder-naming-convention` with `NEXT_JS_APP_ROUTER_CASE` — kebab-case segments, with dynamic segments like `[slug]` permitted).
- Directory names under `components/**` and `features/**` are `kebab-case` (`check-file/folder-naming-convention` with `KEBAB_CASE`).
- Filenames under `components/**` and `features/**` are `kebab-case` (`check-file/filename-naming-convention` with `KEBAB_CASE`); any future `hooks/*` files are `camelCase`.
- `npm run lint` runs `eslint --max-warnings 0` — the ESLint CLI directly, since Next.js 16 removed the `next lint` command. Zero warnings are tolerated; this is a build-breaking gate, not advisory.
- `eslint-plugin-jsx-a11y`'s `flat/recommended` config is enabled in full (not just the narrow subset `eslint-config-next` bundles by default) — every rule it flags fails the zero-warning lint gate above. This catches structural accessibility mistakes (missing `alt`, invalid ARIA, unlabeled controls) at commit time; it cannot check color contrast ratios, which are verified by hand against the WCAG formula per the Accessibility Theme Engine section, not by ESLint.
- **Zero undocumented `eslint-disable` on `jsx-a11y` rules:** a suppression must carry an inline comment citing the specific reason (e.g. a documented WCAG exception, per the Accessibility Theme Engine section) — never a bare disable to silence the linter.

## Automated Lighthouse & axe-core Audits

- **`.lighthouserc.js`** (Lighthouse CI, `pipelines/ci/web.yml`'s `LighthouseCI` job) audits only `/`, `/projects`, and `/log` — `/sign-up` and `/log-in` are deliberately excluded because both mount `TurnstileWidget`, whose third-party `challenges.cloudflare.com` script introduces network-variable noise that would pollute performance scoring and reflects Cloudflare's performance, not this app's. Those two routes still get structural accessibility coverage from the axe-core spec below.
- **Merge-blocking (`error`) thresholds:** `categories:accessibility` ≥ 0.95, `categories:best-practices` ≥ 0.90, `categories:seo` ≥ 0.90. These are near-deterministic structural checks (missing alt text, invalid meta tags, insecure links) with no legitimate reason to regress.
- **`categories:performance` ≥ 0.80 is `warn`, not `error`, pending known-issue remediation.** The live site has pre-existing, untriaged Lighthouse performance findings; hard-gating today would make every PR red regardless of whether it touches performance, training reviewers to ignore the gate. **This must not stay `warn` forever** — promote it to `error` in a dedicated follow-up PR once those findings are resolved, tracked as a deliberate decision per root `AGENTS.md`'s Log-Driven Development rule, not silently left as-is.
- **`tests-e2e/accessibility.spec.ts`** (`@a11y` tag, same locality/tagging discipline as `@visual` — see `home-layout.visual.spec.ts`) runs `@axe-core/playwright`'s `AxeBuilder` against `/`, `/projects`, `/log`, `/sign-up`, and `/log-in`, scoped to `wcag2a`/`wcag2aa`/`wcag21a`/`wcag21aa`/`wcag22aa` tags (WCAG 2.2 AA — this project's actual target; WCAG 2.2 is a strict superset of 2.0/2.1, confirmed against the W3C spec: "Content that conforms to WCAG 2.2 also conforms to WCAG 2.0 and WCAG 2.1" — so the older tags are kept, not dropped; there is no `wcag22a` tag because 2.2 added no new Level A criteria) and asserting zero violations, with `target-size` (the only `wcag22aa`-tagged rule, disabled by default in the installed `axe-core`) explicitly force-enabled via `.options({ rules: { "target-size": { enabled: true } } })` — called *before* `.withTags(...)`, since `.withRules()` cannot be combined with `.withTags()` (they both write `this.option.runOnly` and would silently overwrite each other, confirmed directly against the installed `@axe-core/playwright` source), while `.options()` only touches `.rules` and survives a later `.withTags()` call, which only touches `.runOnly`. This rule's 24px floor is no longer an understatement of this project's bar now that `globals.css`'s own default is 24px too (see the touch target checklist item below) — it is a genuine, redundant, CI-enforced structural check, not decorative. `pipelines/ci/web.yml`'s `E2ETests` job runs `npx playwright test` with no `--grep` filter, so this spec already runs there with no pipeline change.
- **Excluding an element from the axe scan requires a named WCAG exception, not convenience.** The one sanctioned example today is `BrandMark`'s wordmark (`data-brand-wordmark`), excluded under WCAG 2.1 SC 1.4.3's explicit "text that is part of a logo or brand name has no minimum contrast requirement" clause — see `accessibility.spec.ts`'s and `brand-mark.tsx`'s comments. A real contrast defect (e.g. the `--accent` token darkening in `globals.css`) is fixed at the source, never excluded.
- **Viewing Lighthouse HTML reports in CI:** the `LighthouseCI` job (`pipelines/ci/web.yml`) uses the org-installed `blakyaks.azure-pipeline-html-reports` extension's `PublishHtmlReport@1` task to render each page's report as its own tab under the run's **Reports** section. lhci's own output filenames (`lhr-<timestamp>.html`, 9 total for 3 pages × 3 runs) don't identify which page they're for, so `scripts/ci/lighthouse-rename-reports.mjs` runs first: it reads `.lighthouseci/manifest.json` (written because `.lighthouserc.js`'s `ci.upload.target` is `"filesystem"`), keeps only each page's `isRepresentativeRun` (median) entry — the same run `categories:*` assertions actually gate on — and copies it into `.lighthouseci/renamed/<page>.html`, which `PublishHtmlReport@1` then publishes with readable, filename-derived tab names. Full raw output (all 9 runs' HTML/JSON) remains available via the `lighthouse-reports` pipeline artifact for deeper drill-down.
- **`LighthouseCI` runs against a real fixture Postgres, not a DB-less standalone server:** every audited page mounts `AccountNav` via the header, which calls `authClient.useSession()` client-side, hitting `auth.ts`'s Better Auth handler and its `drizzleAdapter(db)` — without a reachable database this 500s on every request and trips the `errors-in-console` audit. The job declares a `postgres:16` service container (top-level `resources.containers`, referenced by the job's `services` key — Microsoft's own documented noncontainer-job pattern, reachable via `localhost:5432`), runs the same `CREATE EXTENSION citext` workaround `docs/adr/0013-cd-migration-pipeline.md` established for the live server, then `npm run db:migrate`, before `npx lhci autorun` — which also needs `DATABASE_URL`/`BETTER_AUTH_SECRET`/`MFA_ENCRYPTION_KEY`/`TURNSTILE_SECRET_KEY` fixture values set so `auth.ts`'s module-level `betterAuth({...})` call doesn't throw. None of these are real secrets — throwaway values scoped to the ephemeral, per-run CI-local container only.

## What "UK GDPR and WCAG 2.2 AA/AAA compliant" Actually Requires You To Do

Stating that requirement as a goal is not the same as verifying it. This section exists because the following gaps were found in this codebase only after being asked to check for each one *by name* - none of them were caught by the existing automated gates (Lighthouse CI, axe-core), and none of them would have been caught by reading a goal statement like "must be WCAG 2.2 AA/AAA compliant" without also reading this checklist. **Every item below is mandatory on every change touching an interactive element, a color pairing, or user-facing data collection - not optional, not "if time permits."**

- **`aria-invalid` paired with `aria-describedby` on every form error state.** Confirmed by direct inspection: `aria-describedby` was wired correctly everywhere, `aria-invalid` was present nowhere in this codebase before it was explicitly asked about. Lighthouse/axe-core's `aria-valid-attr`/`aria-required-attr` rules check that ARIA attributes which *are present* are used correctly - they do not check that a *semantically necessary* attribute like `aria-invalid` is missing entirely. Absence of an optional-but-required-in-context attribute is not what those rules audit for. See the "Form error state" checklist item above.
- **Touch target size defaults to 24×24 CSS px (AA), not 44×44 (AAA) - AAA is an opt-in.** Confirmed by direct inspection of the installed `axe-core@4.13.0` source (`node_modules/axe-core/axe.js`): the `target-size` rule (a) is defined with `enabled: false` - disabled by default, does not run unless a caller explicitly re-enables it, which `tests-e2e/accessibility.spec.ts` now does via `.options({ rules: { "target-size": { enabled: true } } })`; (b) is tagged `wcag22aa` only - now included in that spec's `withTags([...,"wcag22aa"])` scope, so this half of the bar (the 24px AA floor) **is now covered by that automated axe-core check**, not just the manual measurement below; (c) even when run, checks `minSize: 24` (WCAG 2.2 AA SC 2.5.8's 24px floor, matching this project's own default) baked into the rule's own check config with no public `RunOptions.rules[id].options` override exposed by `axe-core`'s own type definitions - the 44px AAA bar (SC 2.5.5) has no axe-core rule at all, at any tag, enablement, or options setting, and never will with the installed version. Lighthouse's own accessibility category score (verified against its published v7 audit-weight table) has no `target-size` entry whatsoever. **The 44px AAA opt-up and the `data-touch-target-force="aaa"` override remain covered only by a real Playwright assertion, not any automated tool**: `tests-e2e/accessibility.spec.ts`'s "touch target size @a11y" describe block measures a real rendered element's `boundingBox()` in both the default (24px) and opted-up (44px) states. See the "Touch target size" checklist item above.
- **Color contrast IS checked by Lighthouse/axe-core (`color-contrast`, WCAG 2.1 SC 1.4.3, 4.5:1 text) - this is the one item in this list the existing pipeline does catch on its own.** It was still independently re-verified against the real relative-luminance formula in this session rather than trusted from `globals.css`'s own comments, and that habit should continue - a passing automated gate is not a substitute for understanding why a value passes, especially for a new color pairing not yet covered by an existing CI run.
- **GDPR disclosure accuracy on `/legal` is not automatable by any tool, including commercial cookie/tracker scanners** - see the "Legal Disclosure Coverage" section immediately below for the full detail and the mechanical (but deliberately partial) check this project does have for it.
- **Keyboard-only operability (Tab/Enter completing a real form) is not what axe-core's structural keyboard checks (`tabindex`, focus-visible presence) prove.** Confirmed by finding zero `page.keyboard.press` calls anywhere in this codebase before `tests-e2e/keyboard-navigation.spec.ts` was added. A structural check that an element is *reachable* is not the same as an end-to-end proof that a user can *complete and submit* a form using only the keyboard.
- **A `<details>/<summary>` disclosure has no automated check that its trigger's accessible name reflects open/closed state** - axe-core/Lighthouse only verify the native `details` role is present, not that a *button-based* disclosure's visible label changes the way `main-navigation.tsx`'s mobile menu ("Menu" → "Close") already does. Found live on `ThemeSelector`, which used a native `<details>` with a static "Theme" label and no `aria-expanded` at all - fixed by converting it to the same controlled-button pattern (WCAG 2.2 SC 4.1.2, Name Role Value). Any new disclosure/dropdown control must use this same controlled pattern, not a native `<details>`, if its trigger's label should reflect state.
- **SC 2.4.11 Focus Not Obscured (Minimum, new in WCAG 2.2, Level AA) has no axe-core/Lighthouse rule at all** - confirmed no automated tool in this pipeline checks that a keyboard-focused element inside an `absolute`-positioned overlay (`ThemeSelector`'s panel, `MainNavigation`'s mobile menu) is never visually hidden behind another element. Manual-Tab-through verification only; not yet covered by a dedicated e2e assertion - a real gap to close in a future slice, not silently accepted as fine because the panels happen to use a high `z-10`.
- **SC 3.3.8/3.3.9 Accessible Authentication is a real, assessed compliance point for this project's own MFA system, not a generic checklist filler.** 3.3.8 (Minimum, AA) is met: no password/one-time-code field blocks paste, and every one uses a correct `autocomplete` token supporting password-manager/browser autofill. 3.3.9 (Enhanced, AAA) is **not** met and cannot be while password remains a factor - it permits no cognitive test at all, even with an alternative, and a password is itself a memorised secret. Only a passwordless method (e.g. a passkey) closes this gap; see `/accessibility`'s assessment table for the full, published statement.
- **SC 2.2.3/2.2.6 (No Timing / Timeouts, AAA) are real, documented exceptions for this project's own MFA challenge window** (`features/auth/mfa/mfa-session-cache.ts`'s `MFA_SESSION_TTL_MS`, 3 minutes) - a deliberate anti-fraud control, not an oversight, but currently with no advance warning before expiry. A countdown warning before that 3-minute window closes would be a real, achievable improvement (still meeting the security requirement of a hard, non-extendable ceiling) that has not yet been built - tracked on `/accessibility`'s own "deliberately not built yet" list rather than silently left off it.
- **The pattern going forward:** when a requirement is stated as a compliance target ("must be UK GDPR / WCAG 2.2 AA/AAA compliant"), treat that as a prompt to walk this exact checklist against the changed files, not as confirmation that the existing automated gates already cover it. If a new class of gap is found that isn't covered by an item above, add a new item here (and, where mechanically possible, a new automated check like `legal-disclosure-coverage.test.ts` or `keyboard-navigation.spec.ts`) in the same change that found it - do not fix the one instance and leave the checklist silent on the general case.

## Legal Disclosure Coverage (`/legal`)

- **No commercial cookie/tracker scanner (Cookiebot, Termly, GDPR.eu's checker, etc.) can verify this page against this codebase.** Those tools crawl a *live* site and detect cookies/scripts *firing in the browser* — they cannot see a server-side third-party call (e.g. an Azure Communication Services send inside a route handler) that has zero client-side footprint. Do not rely on one to catch a missing disclosure here.
- **`features/compliance/known-data-processors.ts` + `features/compliance/__tests__/legal-disclosure-coverage.test.ts`** is this repo's own mechanical check: every registered processor's `sourceSignatures` (an import specifier or outbound hostname) is scanned for across `src/web`, and if found, at least one of its `requiredLegalText` strings must appear verbatim on `app/legal/page.tsx`. Introducing a new third-party processor call site (a new SDK import, a new outbound API call from server or client code) without adding/updating its entry here fails this test on the next `npm run test:unit` — before commit, not after a PR review misses it.
- **This check's real, documented limit: it is presence-only, not scope/purpose-accuracy.** It cannot detect a processor whose disclosure text is present but too narrowly scoped for a new use (exactly what happened when Azure Communication Services' disclosure existed for MFA only while a second, unrelated ACS call site — email verification/reset — shipped uncovered by that wording). Scope accuracy is a semantic judgement no automated tool can make; the root `AGENTS.md` Log-Driven Development log-entry review is the actual backstop for that class of gap, not this test.
- **When adding a call site under an already-registered processor for a new purpose**, updating `/legal`'s prose to cover that new purpose is a required part of the same change, not optional follow-up — the test will not tell you the wording needs broadening, only whether the processor's name is mentioned at all.
