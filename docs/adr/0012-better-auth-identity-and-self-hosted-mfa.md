# Better Auth for identity/session, self-hosted TOTP MFA, citext for email

Devafusion needs a real identity layer for the first time - user
registration, session management, and (per product intent) an eventual
role-gated view of internal content. The chosen stack is **Better Auth**
(session/credential/OAuth core) + **`@better-auth/drizzle-adapter`**
(Postgres via the existing `pg`/`node-postgres` driver) + a **self-built**
TOTP MFA layer (own encrypted column, own verification route, `otpauth`
for RFC 4226/6238 TOTP) rather than Better Auth's own `twoFactor` plugin.
Everything is hosted entirely within this project's own UK South Azure
Postgres instance - no third-party identity SaaS (Okta, Auth0, Clerk),
per UK GDPR data-sovereignty requirements already settled before this
ADR was written.

## Status
Accepted

## Rationale
- **Better Auth over Auth.js (NextAuth)**: Auth.js's own official
  documentation site states plainly, as of this writing, "The Auth.js
  project is now part of Better Auth" - Better Auth is the actively
  developed successor, built by the same authors/company
  (`Auth.js © Better Auth Inc.`), not an unrelated community fork.
  Starting a brand-new identity layer on Auth.js today would mean
  planning a near-immediate migration; starting directly on Better Auth
  avoids that.
- **Reuse the existing `pg`/`node-postgres` driver, no `postgres-js`**:
  `@better-auth/drizzle-adapter` explicitly supports `provider: "pg"`,
  confirmed against its own docs - there is no reason to add a second
  Postgres driver to this project's dependency tree (root AGENTS.md,
  Standardized Tooling) when the one already running
  (`db/client.ts`, ADR-0011) is directly compatible.
- **Core schema generated by Better Auth's own CLI, not hand-written**:
  `npx auth@latest generate --adapter drizzle --dialect postgresql` was
  run for real against this project's actual `db/client.ts` to produce
  the authoritative `user`/`session`/`account`/`verification` table
  definitions, rather than transcribing from documentation examples that
  could be stale or incomplete. The generated schema already applies
  `onDelete: "cascade"` on every foreign key back to `user.id`
  (`session.userId`, `account.userId`) - Better Auth's own default
  already satisfies the GDPR "right to be forgotten" cascade-delete
  requirement without any custom schema work.
- **`@better-auth/cli` (the package) is itself deprecated** - npm reports
  it as "Package no longer supported." The correct, current package is
  `auth` (invoked as `npx auth@latest generate`), confirmed against
  Better Auth's own CLI documentation page. Any future reference to
  `@better-auth/cli` in a tutorial or AI-generated snippet should be
  treated as stale.
- **Self-hosted MFA, not Better Auth's `twoFactor` plugin**: the plugin
  was evaluated and rejected specifically for its secret-at-rest
  handling. Its own schema documentation states it stores
  `twoFactorBackupCodes` encrypted but `twoFactorSecret` (the primary
  TOTP seed) as plain text - and Better Auth's `databaseHooks` system
  only documents `create`/`update` "before" hooks, with no symmetric
  read-side decrypt hook the plugin's own internal TOTP-verification
  endpoint would invoke. Attempting to encrypt the column via a write
  hook without a matching read-side decrypt path the plugin actually
  uses would silently break verification, not secure it. Rather than
  accept plaintext storage of a credential-equivalent value or fight the
  plugin's internal boundary, this project uses Better Auth only for
  session/credential/OAuth core, and builds MFA entirely itself: an
  application-owned, envelope-encrypted `two_factor_secret` column
  (key sourced from Key Vault, encrypted/decrypted only inside this
  project's own route handler - Postgres itself never holds recoverable
  plaintext) and a self-written TOTP verification route using
  **`otpauth`** (RFC 4226/6238-compliant, actively maintained, zero
  native/binary dependencies, confirmed via its own repository and
  README's explicit RFC citations for its search-window security
  guidance).
- **`citext` for case-insensitive email lookups**: confirmed present on
  Azure's own extension allowlist for every currently supported Postgres
  version, including this project's pinned version 16 (Microsoft's
  extension-version documentation lists `citext` 1.6 for Postgres 16).
  It still requires one explicit, Terraform-managed step - adding it to
  the server's `azure.extensions` configuration parameter
  (`azurerm_postgresql_flexible_server_configuration`) - it is not
  enabled merely because the base extension exists upstream in
  PostgreSQL itself.

## Considered Options
- **Auth0 / Okta / Clerk / Entra External ID (B2C)** - rejected for this
  slice: all are third-party-hosted identity SaaS, in direct tension
  with the UK GDPR data-sovereignty requirement (identity data, sessions,
  and MFA secrets must stay inside this project's own UK South Azure
  Postgres instance, not a third-party vendor's infrastructure and
  region). A dedicated pros/cons discussion of enterprise IdP options
  (Okta/Entra External ID) was deliberately had and closed in favour of
  a self-hosted approach before this ADR was written.
- **Auth.js (NextAuth) directly** - rejected: superseded by Better Auth
  per its own homepage notice; adopting it new today would mean an
  almost-immediate forced migration.
- **Better Auth's built-in `twoFactor` plugin** - rejected: plaintext
  `twoFactorSecret` storage with no read-side hook available to encrypt
  it transparently; see Rationale.
- **`pgcrypto` column-level encryption** (`pgp_sym_encrypt`/
  `pgp_sym_decrypt`) - considered as an alternative to application-layer
  envelope encryption. Rejected for the same underlying reason as the
  plugin: Better Auth's plugin (if used) would still read the column via
  its own adapter expecting a raw, immediately-usable secret, with no
  awareness that SQL-level decryption is needed - the transparency
  problem is identical regardless of which side does the encrypting.
  Moot once the plugin itself was rejected, since this project's own
  route handler can decrypt in application code just as easily.
- **`postgres-js` driver** - rejected: redundant with the existing `pg`
  driver already proven working (ADR-0011, local Docker Postgres 16
  migration test); no functional need to run two Postgres drivers.

## Consequences
- Better Auth's core tables (`user`, `session`, `account`,
  `verification`) are the authoritative, CLI-generated schema - do not
  hand-edit their column definitions; re-run `npx auth@latest generate`
  if Better Auth's own config/plugins change what it expects, and diff
  the result before committing, the same discipline already established
  for `drizzle-kit generate` (ADR-0011, `infrastructure/AGENTS.md`
  PostgreSQL section).
- A new `two_factor_secret` (encrypted at the application layer) and
  `two_factor_enabled` column/table pairing is this project's own code,
  not Better Auth's - it must be migrated, tested, and reasoned about
  independently of Better Auth's own migration path.
- The Key Vault secret used as the envelope-encryption key for
  `two_factor_secret` is a new, manually-provisioned secret value
  (ADR-0004's sanctioned manual step), read by the application at
  runtime exactly like `DATABASE_URL`'s password component - never
  written by Terraform, never a literal anywhere in code or comments
  (root AGENTS.md).
- `citext` requires a Terraform-managed `azure.extensions` allowlist
  change (`infrastructure/app/modules/postgresql`) before any migration
  that uses the `citext` column type can run against the live server -
  sequencing matters: the extension must be allowlisted first, or the
  migration will fail against the real database (though it can still be
  authored and reviewed beforehand, same as any other infrastructure
  dependency ordering in this project).
- Local development/testing reuses the already-proven `docker run
  postgres:16` workflow (`src/web/AGENTS.md`, established this session)
  with no changes - Better Auth's schema and this project's own MFA
  table migrate through the same `drizzle-kit generate`/`migrate`
  pipeline already in place.
- The actual registration/login UI, the role-gated content-visibility
  feature this identity layer was originally motivated by, and the CD
  pipeline's `Migrate` stage extension are follow-up slices, not built
  as part of this ADR - this ADR and its accompanying schema/tooling
  changes establish the identity foundation only.
- **`log_entries` (ADR-0011) was removed from `db/schema.ts` for this
  slice, along with its three dependents** (`DrizzleLogEntryRepository`,
  its test, and `log-entries.zod.ts`/`zod-openapi-setup.ts`/
  `scripts/generate-openapi.ts`): the single migration this slice
  generates and applies would otherwise have chained on top of an
  already-deferred, no-consumer table, forcing that deferred decision
  through by a journal-ordering technicality rather than a real product
  decision. All of it is recoverable from git history as one unit once
  the role-gated visibility feature (which needs `log_entries`) is
  actually being built - restore the table and all three files
  together, not piecemeal.
